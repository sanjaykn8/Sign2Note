# Sign2Notes

Sign2Notes turns sign-language communication into reusable study
material — running entirely on a local laptop, using a constrained-
vocabulary recognition model trained on **FDMSE-ISL**. Three modes cover
different ways of capturing that communication:

1. **Video Upload** — upload a pre-recorded clip; long-video-capable,
   Viterbi-smoothed recognition.
2. **Live Webcam** — sign in real time; a running session history you can
   edit, then turn into notes on demand.
3. **Live Transcription** — sign in real time (webcam or a shared tab/
   window/screen) and watch a live gloss transcript build up; one
   "Stop & Generate" click turns it into both a natural-language
   transcript and structured notes, without ever calling the LLM while
   you're still signing.

Recognition uses MediaPipe Holistic (hand + body pose + face landmarks,
see `FEATURE_SCHEMA.md`) feeding a lightweight Temporal CNN (an optional
CNN+BiLSTM experiment also exists, off by default — see "Training"
below). Notes and transcripts are generated by a local LLM when available
(three genuinely different note styles: concise/detailed/academic).
Exports are Markdown, Text, PDF, and Word (.docx), all generated
client-side. Everything can also run **distributed** across multiple
laptops — see "Distributed architecture" below.

## Quick Start

```powershell
# 1. Clone and enter the project
git clone <repo-url> Sign2Note
cd Sign2Note

# 2. Python environment
python -m venv .venv
.venv\Scripts\activate
pip install -r ml_service/requirements.txt

# 3. Node services
cd backend;  npm install; cd ..
cd frontend; npm install; cd ..

# 4. Place the FDMSE-ISL dataset (see "Dataset" below) at:
#    data/data_meta/   and   data/FDMSE-ISL/

# 5. Extract keypoints, build the vocabulary, train
python ml_service/feature_extraction.py --dataset_format fdmse --metadata_csv data/data_meta/metadata_400.csv --dataset_root data/FDMSE-ISL --out_dir data/features --frame_skip 8 --workers 4
python ml_service/build_index.py --dataset_format fdmse --metadata_csv data/data_meta/metadata_400.csv --min_samples 10
python ml_service/train.py --epochs 20 --batch_size 32 --num_workers 0

# 6. Start all three services (separate terminals)
cd ml_service; python -m uvicorn api:app --host 127.0.0.1 --port 8000
cd backend;    npm start
cd frontend;   npm run dev

# 7. Open http://localhost:8080
#    "/"        -> upload a video
#    "/webcam"  -> live webcam session
```

Deterministic notes work immediately, with no LLM required. For LLM-backed
notes, see "LLM notes" in `SETUP.md`.

## Pipeline

```text
Video (upload)                       Webcam (live)
     |                                    |
     v                                    v
MediaPipe keypoints              MediaPipe keypoints
(server-side, per-frame)         (in-browser, WASM)
     |                                    |
     v                                    v
Sliding temporal windows          Sliding keypoint buffer
     |                                    |
     v                                    v
Temporal CNN (ONNX/PyTorch)       Temporal CNN (ONNX Runtime Web)
     |                                    |
     v                                    v
Viterbi/HMM smoothing             Real-time confidence gating
+ duplicate collapse              + stability smoothing
     |                                    |
     v                                    v
Ordered, timestamped              Session gloss history
gloss sequence                    (label, confidence, timestamp)
     |                                    |
     +--------------+---------------------+
                     v
          Template Engine  or  Local LLM
          (always available)   (Ollama / llama.cpp)
                     |
                     v
          Structured Markdown notes
```

See `ARCHITECTURE.md` for the full breakdown, including a bug we found and
fixed in the sliding-window normalization while building long-video
support.

## Dataset

The project trains on **FDMSE-ISL** (not WLASL — WLASL only appears in
this codebase as a legacy/previous-development dataset format still
supported by `feature_extraction.py --dataset_format wlasl` for anyone
with existing WLASL-based work, but it is not what the shipped model uses
or what `build_index.py` defaults to).

```text
data/
  data_meta/
    classes.txt              # full 2,002-class legend
    classes_400.txt          # legend for the 400-class subset
    metadata.csv             # all 2,002 classes, 40,034 clips, 20 signers
    metadata_400.csv         # curated 400-class subset (20 samples/class) - recommended default
    metadata_atomic.csv      # single-gesture signs only (1,099 classes)
    metadata_composite.csv   # multi-word/compound signs only (352 classes)
  FDMSE-ISL/
    data/
      s0001/front/*.mp4
      s0002/front/*.mp4
      ...
```

Each metadata CSV has columns `id,video_dir,video_name,class,split`:
- `video_dir` -- path to the clip, **relative to `data/FDMSE-ISL`**
  (e.g. `data/s0015/front/s0015_f_w000842.mp4`)
- `class` -- the gloss label (e.g. `"Whistle"`) -- used directly as the
  training label, no separate lookup table needed
- `split` -- the dataset's own train/val/test assignment. `train.py` uses
  this when it's present and has usable train/val rows -- see "Training"
  below -- and `evaluate.py` uses the `test` rows exclusively (never
  train/val) for a leakage-free final evaluation.

`metadata_400.csv` is the recommended starting vocabulary -- training all
2,002 classes is not realistic for a demo-scale model or a single laptop
GPU. `metadata_atomic.csv` (single-gesture signs, 1,099 classes) is a good
middle ground if you want broader coverage and can tolerate a longer
extraction/training run. Use `metadata.csv` (the full dataset) for the
complete-vocabulary experiment once the 400-class pipeline is working end
to end.

`feature_extraction.py --dataset_format fdmse` reads a metadata CSV and
writes one `.npy` keypoint file per clip (video filename stem as the
video_id -- these are unique across all 20 signers), plus a
`feature_meta.json` describing the schema version/dims/extraction config
(see `FEATURE_SCHEMA.md`). `build_index.py` turns a metadata CSV plus the
extracted `.npy` files into `data/index.csv` (video_id, label, split) and
`config/vocab.json` (label2id/id2label), filtering to classes with at
least `--min_samples` examples.

## Training

```powershell
# 1. Extract keypoints (hand+body+face, schema v2 -- see FEATURE_SCHEMA.md)
python ml_service/feature_extraction.py `
  --dataset_format fdmse `
  --metadata_csv data/data_meta/metadata_400.csv `
  --dataset_root data/FDMSE-ISL `
  --out_dir data/features_v2 `
  --frame_skip 8 `
  --workers 4

# For the full-vocabulary experiment instead of the 400-class fast one:
#   --metadata_csv data/data_meta/metadata.csv

# 2. Build the vocabulary + index
python ml_service/build_index.py `
  --dataset_format fdmse `
  --metadata_csv data/data_meta/metadata_400.csv `
  --min_samples 10

# 3. Train -- default architecture is temporal_cnn; uses the official
#    train/val split from data/index.csv's `split` column automatically
#    when it's present (falls back to a random split, with a console
#    warning, if it isn't -- see split_utils.py)
python ml_service/train.py `
  --feature_dir data/features_v2 `
  --epochs 20 --batch_size 32 --num_workers 0

# Optional: the CNN+BiLSTM experiment (project brief section 9) --
#    NOT the default, only worth adopting if it measurably beats
#    temporal_cnn on the metrics evaluate.py reports (RULE 2):
#   python ml_service/train.py --architecture cnn_bilstm --feature_dir data/features_v2

# 4. (train.py also exports ONNX automatically at the end)
```

Outputs:
```text
models/sign_recog_v2/checkpoints/best.pt
models/sign_recog_v2/checkpoints/demo.pt
models/sign_recog_v2/sign_recog.onnx
models/sign_recog_v2/sign_recog.json    # {input_dim, max_len, num_classes, architecture, feature_schema_version, ...}
```

Every checkpoint records its own `architecture`, `feature_schema_version`,
a `vocab_hash` (for detecting vocabulary drift), the full training
config, and `best_val_accuracy` -- see `checkpoint_meta.py`. Test-set
metrics are **not** part of the checkpoint; they only exist if you run
`evaluate.py` (below), and are written to a separate `eval_results/`
directory so "validation accuracy" (used for early stopping/checkpoint
selection during training) and "test accuracy" (measured once, after
training, on held-out data never seen during training) can never be
confused for each other (RULE 3).

### Recommended settings for an RTX 4050 6GB

| Setting | Recommendation | Why |
|---|---|---|
| `--batch_size` | 32 (try 64 if VRAM allows) | The model is small (1D-conv TemporalCNN), so 6GB comfortably fits a moderate batch |
| Sequence length (`max_len`, set at `build_index.py`/dataset level, not a train.py flag) | Keep at the dataset's default window length unless you have a specific reason to change it | Longer windows cost more compute per sample for limited accuracy gain on short isolated signs |
| `--frame_skip` (at extraction time) | 8 | Halves keypoint volume vs. `frame_skip=4` with little accuracy cost for isolated-sign recognition; raise further only if extraction is a bottleneck |
| `--num_workers` | **0 on Windows** | Avoids multiprocessing spawn errors in PyTorch's `DataLoader` on Windows; raise on Linux/Mac if I/O-bound |
| AMP (mixed precision) | Not required at this model size, but safe to enable if you add it -- the model is small enough that AMP mainly helps if you significantly scale up `max_len` or batch size |
| Expected VRAM | Well under 6GB at these settings -- this model was deliberately kept lightweight (1D convolutions, not a Transformer) specifically so it fits both a 6GB laptop GPU for training AND a browser via WASM for the live webcam demo |

`INFER_CHUNK_SIZE` (env var, default 64) controls how many sliding windows
are batched per forward pass **at inference time** for long videos --
lower it if you're inference-testing on a more memory-constrained machine
than you trained on.

## Evaluation

`evaluate.py` is a dedicated script, separate from training, that
measures a checkpoint against the official **test** split only (never
train/val -- `split_utils.resolve_test_indices()` raises rather than
silently substituting another split if no `test` rows exist):

```powershell
python ml_service/evaluate.py `
  --checkpoint models/sign_recog_v2/checkpoints/best.pt `
  --index_csv data/index.csv `
  --feature_dir data/features_v2 `
  --confusion_matrix_png
```

Writes `models/sign_recog_v2/eval_results/results.json` (machine-readable)
and `results.txt` (human-readable): Top-1/Top-3/Top-5 accuracy, macro F1,
weighted F1, and per-class precision/recall/F1/support for every class
(including classes with zero test examples, reported as such rather than
omitted). `--confusion_matrix_png` additionally renders a heatmap --
per-class tick labels are only drawn for vocabularies of 60 classes or
fewer (illegible/slow to render otherwise; the heatmap itself is still
useful without them).

### Why 83.5% val accuracy isn't the number to trust yet

This project's earlier, hand-only (schema v1) model reached ~83.5%
**validation** accuracy on a random split -- not the official FDMSE-ISL
test split, and not schema v2 (hand+body+face). It's a real historical
result, worth keeping as a reference point, but it shouldn't be quoted as
"the" accuracy of the current pipeline: nothing in this repository has
actually been retrained end-to-end and evaluated on the official test
split with schema v2 features (training needs a working PyTorch
installation and the real dataset, neither of which were available while
this pipeline was built -- see `DEVELOPER_GUIDE.md`). Run the training +
evaluation commands above yourself and report what `evaluate.py` actually
prints; don't reuse 83.5% for a different schema/split/architecture.

### Why the pipeline uses windows + Viterbi

FDMSE-ISL (like WLASL before it) is word-level: each clip is one isolated
sign, not a sentence-level aligned continuous-signing dataset. To handle
videos containing a *sequence* of signs, inference breaks the extracted
keypoint sequence into overlapping windows, predicts a gloss distribution
per window, and uses Viterbi smoothing to favor stable transitions and
collapse repeated predictions into single events -- see `ARCHITECTURE.md`
for the full design and a normalization bug we found and fixed while
building this.

## Live webcam demo

Click "Live Webcam" in the nav, then **Start Session** and sign -- a
"Current Sign" display and a running "Sign History" update live. Use
**Pause**/**Resume** to freeze recognition without losing the session, and
per-event pencil/trash icons or the **Undo** button to fix or remove a
misrecognized sign. Click **Generate Notes** when done (or **Stop
Session** first if you want to review the history before generating).
**Clear Session** resets everything. See `ARCHITECTURE.md` for the full
client-side pipeline and `PRIVACY.md` for exactly what does/doesn't leave
the browser.

## Live Transcription mode

Click "Live Transcription" in the nav. Choose a source -- **Webcam**, or
**Screen / Tab** (via the browser's own `getDisplayMedia` picker, for
transcribing sign-language content already playing on your device; not
every browser supports this, the button disables itself when it doesn't)
-- then **Start**. Recognized signs build up into a running gloss
transcript live, with the same edit/delete/undo controls as the webcam
page. The LLM is **not** called while you're signing -- only when you
click **Stop & Generate**, which does three things in one step: freezes
the gloss sequence, then produces both a natural-language transcript
(flowing prose) and structured notes from it. If generation fails (LLM/
network down), your recognized glosses are preserved and a **Retry**
button re-attempts without losing the session. See
`ml_service/notes_generator.py`'s module docstring for why the transcript
and the notes are genuinely different outputs (not the same thing with
headers stripped), and `ARCHITECTURE.md` for the full state flow.

## LLM notes and transcripts

Two modes, always available in the UI, for both notes and transcripts:

- **Deterministic template** (`notes_mode="template"`) -- no LLM needed.
  For notes: groups recognized glosses into Key Concepts/Questions/Tasks
  sections where it recognizes structuring keywords, otherwise a flat
  list. For transcripts: a literal "X, then Y, then Z" rendering, clearly
  labeled as not natural prose.
- **Local LLM** (`notes_mode="llm"`) -- calls a local Ollama or llama.cpp
  server, configured via `ml_service/.env` (`LLM_PROVIDER`, `LLM_MODEL`,
  `LLM_BASE_URL` -- see `.env.example`). Falls back to the deterministic
  template automatically if the server is unreachable -- you always get
  something back.

Notes come in three genuinely different styles -- **concise**, **detailed**,
**academic** -- each with its own prompt structure and its own template
fallback rendering, not one generic template with a style word swapped
(see `notes_generator.py`). Transcripts don't have a style option: a
transcript's job is to read like a rough record of what was signed, in
order, regardless of register.

Generated notes always go through **Preview -> Edit -> Export**, never a
direct download: click **Edit** to fix a misrecognized gloss before it
leaves the app, then export as **Markdown**, **Text**, **PDF**, or
**Word (.docx)** (all generated client-side, no extra backend round-trip).
The .docx export is deliberately simple -- a title, date/duration, and the
notes as headings/bullets/paragraphs with bold/italic preserved -- not an
elaborate report template, and it never includes internal details
(confidence scores, model version) unless they're already part of the
notes text itself.

## Distributed architecture

The recognition model can run on more than one laptop. The main
laptop/server hosts the recognition model (as a fallback), the LLM, and
the API gateway; other laptops can run the browser client with their own
local ONNX model, or without one.

```text
CLIENT (browser)
  ↓
Local recognition model available? (GET /model/meta, checked against
  the browser's own feature schema/ONNX -- see RULE 26)
  ├── YES → keypoints → local ONNX model → glosses, entirely in-browser
  │           (this is what Webcam.tsx / LiveTranscription.tsx already do)
  └── NO  → keypoints → POST /recognize → MAIN SERVER's model → glosses
              (frontend/src/lib/api.ts: recognizeFromFeatures())
  ↓
glosses (never video, never raw keypoints beyond the /recognize call above)
  ↓
POST /notes and/or POST /transcript → MAIN SERVER's LLM → notes/transcript
  ↓
CLIENT
```

Two things this deliberately does NOT do:
- **A client with no local model and no local landmark extraction cannot
  skip straight to "send glosses"** -- there's nothing to send yet. It
  must go through `/recognize` (sending keypoints, which its browser can
  still extract locally via MediaPipe) or, as a last resort, `/process`
  (sending the actual video) -- never a client claiming glosses it has no
  way to have produced.
- **The LLM is never asked to recognize signs**, and the recognition
  model is never asked to write prose -- `/recognize` returns glosses
  only, `/notes`/`/transcript` take glosses only. See
  `ml_service/notes_generator.py`'s module docstring on the three output
  layers.

`GET /model/meta` is how a client checks compatibility before trusting
its own local model: it returns the server's `feature_schema_version`,
`architecture`, and `vocab_hash`, so a client can detect "my local model
is stale" and fall back to `/recognize` instead of silently producing
wrong predictions (see `ml_service/checkpoint_meta.py`). The frontend
doesn't yet have this fallback wired into its UI automatically -- 
`recognizeFromFeatures()` exists and is tested, but `Webcam.tsx`/
`LiveTranscription.tsx` currently always assume a local model is
available (they block on `GET /model/onnx` succeeding). Automatically
switching to `/recognize` when that fails is a natural next step, not yet
built.

## What Was Changed

This MVP upgrade modified the following, building on the existing
architecture rather than rewriting it (`dataset.py`'s augmentation,
`train.py`'s training loop/ONNX export, and `model.py`'s TemporalCNN were
already solid and were left alone):

**Long-video support**
- `ml_service/inference_viterbi.py` -- added `viterbi_events()` for
  timestamped, duplicate-collapsed gloss sequences, built on a refactored
  (but behaviorally-verified-identical) `_viterbi_path()` shared with the
  original `viterbi_decode()`.
- `ml_service/infer.py` -- added chunked windowed inference
  (`INFER_CHUNK_SIZE`) so memory/compute stays bounded regardless of video
  length; added timestamp computation from video fps + frame_skip +
  stride. **Found and fixed a real bug**: `_window_batch` was normalizing
  the entire long video once globally instead of per-window like training
  does -- this actively broke multi-sign detection in longer videos (see
  `ARCHITECTURE.md` for the full story).
- `ml_service/api.py` -- `/process` now returns an `events` field (ordered,
  timestamped, collapsed) alongside the existing `gloss_list`.

**Live webcam**
- New `frontend/src/lib/webcamPipeline.ts` -- pure logic (keypoint
  construction, normalization, sliding buffer, real-time smoothing),
  numerically cross-validated against the Python training pipeline and
  covered by 19 unit tests.
- New `frontend/src/lib/onnxSession.ts`, `handLandmarker.ts` -- browser
  wrappers around `onnxruntime-web` and `@mediapipe/tasks-vision`.
- New `frontend/src/pages/Webcam.tsx` -- the live session UI.
- New backend endpoints: `GET /model/meta`, `GET /model/onnx` (so the
  browser can run inference itself), `POST /notes` (generate notes from
  an already-recognized gloss list, no video/keypoints involved).
- New `backend/server.js` proxy routes for the above.

**Note generation**
- `ml_service/infer.py` -- replaced the hard-coded llama.cpp-only client

## Known Limitations

Being explicit about what this is and isn't, per the project's own
development principles:

- **Constrained vocabulary, not general ISL translation.** The model
  recognizes isolated signs from whatever vocabulary it was trained on
  (400 classes by default) -- it does not perform continuous,
  general-purpose Indian Sign Language translation, and should not be
  presented as such.
- **Isolated-sign vs. continuous-language gap.** FDMSE-ISL, like WLASL, is
  a word-level dataset (one clip = one sign). The sliding-window + Viterbi
  approach lets the system report *multiple* signs from a longer video,
  but this is pipeline engineering on top of an isolated-sign classifier --
  it is not the same as a model trained on continuous, sentence-level,
  co-articulated signing, which would require a sequence-aligned dataset
  and likely a CTC/sequence model.
- **Model accuracy depends heavily on training data coverage** -- camera
  angle, lighting, signer variation, and vocabulary size all matter a lot
  at this scale. `/process`'s "always return a result" fallback
  (majority-vote best guess when nothing crosses the confidence threshold)
  is a deliberate UX choice for the upload flow, not a claim that the
  fallback result is reliable -- see `ARCHITECTURE.md`.
- **The live webcam's real-time smoothing is a simplified heuristic**
  (N consecutive agreeing predictions -> commit), not the same
  Viterbi/HMM decoding the batch upload path uses -- a live stream doesn't
  have the whole clip's probabilities available up front the way a
  finished video upload does. Documented in `ARCHITECTURE.md`.
- **Neither the webcam nor the live transcription feature has been
  tested in a real browser with a real camera as part of this work.**
  Both share the same underlying pipeline
  (`useSignRecognitionSession.ts`). Everything reachable without a
  browser has been verified for real: the pure logic
  (`webcamPipeline.ts`, `featureSchema.ts`) is unit-tested and numerically
  cross-validated against the Python reference implementation (including
  a cross-language golden-vector test, not just each side's own tests),
  the Live Transcription page's stop/generate/retry state flow is
  covered by an actual rendered-component test (mocking only the camera/
  model layer), the whole frontend type-checks cleanly and builds
  successfully with Vite (proving all imports/dependencies resolve), and
  the backend endpoints it calls (`/model/meta`, `/model/onnx`, `/notes`,
  `/transcript`, `/recognize`) are tested end-to-end (Python) or written-
  and-reviewed (torch-dependent files, since PyTorch couldn't run in this
  environment -- see `DEVELOPER_GUIDE.md`). What hasn't been exercised is
  the actual runtime combination of `getUserMedia`/`getDisplayMedia`,
  MediaPipe's WASM Holistic tracking, and ONNX Runtime Web's WASM
  inference together in a live browser tab -- that requires an actual
  browser + camera, unavailable in the environment this was built in.
  Test this first before relying on it for a live demo.
- **`train.py` uses FDMSE-ISL's official `split` column** (written into
  `data/index.csv` by `build_index.py`) when it's present and has usable
  train/val rows, and falls back to a random split with a loud console
  warning otherwise -- never silently. The official split was *not* used
  for schema v1 / the 83.5% baseline number quoted elsewhere in this
  doc; that number should be read as "random-split validation accuracy,"
  not a result from the official split.
- **Hardware target is a single 6GB-class laptop GPU** (or CPU/browser
  WASM for the live demo) -- the model is deliberately small; don't expect
  large-model-level accuracy.
- **LLM-backed notes depend on a local server being available** (Ollama
  or llama.cpp) -- the deterministic template mode is the reliable
  fallback and works with zero external dependencies.
